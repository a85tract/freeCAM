# The implementation-progress dashboard

`https://a85tract.github.io/freeCAM/progress/` answers, from committed records
only: which processes are callable from Python, which have a dedicated Python
class, which numerical kernels each process contains, and which kernels can be
called independently, replaced inside a model run, and verified against the
original Fortran.  It is a published snapshot of committed records, not a live
HPC job monitor.

## How it is produced

```bash
uv run python tools/export_progress_snapshot.py          # write web/progress/public/progress.json
uv run python tools/export_progress_snapshot.py --check  # is the committed snapshot current?
uv run pytest tests/unit/test_progress_snapshot.py -q    # the exporter's tests
cd web && npm run typecheck && npm test && npm run build:progress
```

The exporter (`freecam.pi_cam.progress`) joins committed sources, each the
authority for its own facts, and refuses ambiguous joins, unknown schemas, and
any output string naming a personal path, machine or account.  The snapshot is
deterministic: `content_hash` covers everything except the `volatile` block
(commit, branch, generation time), which the Pages build re-stamps after
proving the content current.

## Which records update which status

| Displayed fact | Source of truth | Regenerated by |
| --- | --- | --- |
| Process identity, default order, enabled state, display names, the additional callable catalog | `web/public/catalog.json` | `tools/export_workflow_catalog.py` |
| Dedicated Python classes, per-action classification and activity | `validation/physics_kernel_decoupling.json` (`actions`) | `tools/build_physics_kernel_coverage.py` |
| Candidate kernels and their call relationships | `validation/pi_cam_kernel_api_closure.json` (identity and relations only -- its cached evidence blocks are never read, because they go stale against the ledger) | `tools/build_pi_cam_kernel_api_closure.py` |
| Tracked kernels, contracts, evidence lists, in-model gates | `validation/physics_kernel_decoupling.json` (`kernels`) | `tools/build_physics_kernel_coverage.py` |
| Contract available / Adapter built / Independently callable / Standalone replay verified | the validation records those evidence lists name (`pi_cam_<kernel>_standalone_build.json`, `pi_cam_<kernel>_frame_replay.json`, `*_vs_capture.json`, `pi_cam_<kernel>_module_state.json`), each opened and verified | the standalone build, capture and replay tooling |
| In-model replacement and its mechanism (pause or hook) | `native/pi_cam/segment_runners.yaml` and `native/pi_cam/hooks.yaml` | `tools/generate_pi_cam_pausable_runners.py`, by hand for hooks |
| Original-kernel replacement BFB, scoped per process | the gate records the ledger names, opened for their per-process replacement counts and their `_vs_oracle` companions | the 512-rank 50-step gates |
| Symbol-redirection feasibility and blockers | `validation/pi_cam_kernel_api_redirectable_calls.json` | `tools/audit_pi_cam_call_relocations.py` |
| Historical failures | `validation/*failure*.json`, attributed by their own `kernel` / `segmented_original_kernels` fields | kept forever; never deleted by a later success |
| Counting entries and blind spots per candidate | `validation/pi_cam_kernel_observability.json` | `tools/build_pi_cam_kernel_observability.py` |
| Observed / not-observed / unknown per run, per process | `validation/pi_cam_kernel_runtime_coverage_50step.json`, `_1month.json` | an observation gate (`PYCAM_OBSERVE_KERNELS=1` on a counting image) merged by `tools/record_kernel_runtime_coverage.py` |

After changing any of those, run the exporter and commit the refreshed
`web/progress/public/progress.json`; CI's `--check` fails the deployment when
the committed snapshot is stale.

## Two levels, never conflated

A process page separates **core kernels** -- the ones its Python class exposes
for replacement, from the ledger's per-action list, each labeled with the
class that owns it (for `cloud_macro_microphysics` that is `Macrophysics` and
`Microphysics`, composed into `CloudMacroMicrophysics`) -- from the **candidate
numerical functions**: everything the call-tree inventory reaches from the
process recursively, per-point helpers and saturation/packing libraries
included.  Candidates are statically reachable, not necessarily executed, and
exposing a process does not expose every candidate inside it.

## Observation runs

The page's run selector offers the validated observation runs (one month
preferred).  Execution evidence is per process: a kernel observed in one
process is never marked observed in another, per-process capability bars
count only the kernels observed in that process in the selected run, and the
execution inventory names the gaps (partially covered or uninstrumented
candidates).  With no validated observation record the page says *No
validated observation run available* and labels every fallback denominator as
static -- never silently.

## Status vocabulary

`available`, `not-implemented`, `needs-binding`, `not-assessed`, `verified`,
`not-verified`, `failed`, `historical-evidence`, `not-applicable`.  A build is
not an execution test; execution inside a parent process is not
independent-call proof; a redirectable symbol is not an implemented hook; a
replacement gate verifies only the process and call site it ran.  Missing
records produce an explicit unverified state, never an invented success, and a
process without inventory shows *Not inventoried*, not 0/0 = 100 %.

## How it is published

`.github/workflows/pages.yml` builds one composite site per deployment: the
homepage from `main`, the dashboard from `physics-kernel-api-closure`,
assembled and pushed to `gh-pages` together, so neither publication can delete
the other.  Pushes to either branch (and manual dispatch) republish the whole
site; pull requests build previews without publishing.  The workflow file must
stay consistent on both branches until they converge; production always builds
the homepage from `main`.  `site-manifest.json` at the site root records the
exact commits of both halves.
