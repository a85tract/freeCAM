# The kernel-API closure: inventory of the PI-atm physics call tree

freeCAM opens CAM physics to Python one numerical kernel at a time.  The
[decoupling ledger](../validation/physics_kernel_decoupling.json) follows the
kernels that are already open; this page is about everything else: the
complete set of procedures the configured physics step can reach, so that
opening the rest is a list to work through rather than a search.

The record is
[`validation/pi_cam_kernel_api_closure.json`](../validation/pi_cam_kernel_api_closure.json),
generated by `tools/build_pi_cam_kernel_api_closure.py` from the pinned iCESM
source and the rules in
[`native/pi_cam/kernel_api_closure_rules.yaml`](../native/pi_cam/kernel_api_closure_rules.yaml).
`--check` proves the committed record still matches the pinned source, the
rules, the generator and the reference case's configuration; the unit suite
runs that check.

## How the tree is built

- **The build's sources, in the build's order.** The rules list the
  directories of the reference case's `Filepath`; the first directory holding
  a basename wins, exactly as the CESM build resolves it (so the RRTMG copies
  of `radiation`, `cloud_rad_props` and `radconstants` are the ones analysed,
  and CARMA, CLUBB, WACCM and CAM4 code is not).  The `genf90` templates are
  expanded the way the build expands them.
- **The configuration's macros.** Every file goes through `cpp` with the
  case's `CESM_cppdefs` and the machine macros (`SPMD`, `MODAL_AERO_3MODE`,
  `PCOLS=16`, ...), verified against the image manifest's compile command.
  Lines the preprocessor removes never count; every surviving line under a
  conditional carries its condition.
- **Fortran scoping, not name matching.** fparser parses each file; every
  `call` and every reference that could be a function (`Part_Ref`,
  structure-constructor-shaped references) is resolved through locals,
  dummies, host association, `use` with `only` and renames (transitively
  through re-exporting modules), generic interfaces, internal procedures,
  external units, `associate` aliases and type-bound bindings.  A name that
  resolves to a variable or a type is not a call; a name that resolves to
  nothing is recorded as unresolved rather than dropped.
- **Every call site, with its context.** Each site records the original
  line, the preprocessor condition, the enclosing `if`/`select case`
  branches (with negations for `else`), the loop depth, and whether the
  callee is a plain `call`, a function inside an expression, or an actual
  argument of another call.
- **Configuration guards, decided or left open.** Branch conditions are
  evaluated tri-state against the reference run's namelist selectors
  (`deep_scheme`, `microp_scheme`, `use_gw_oro`, ...), the case's build
  options (`cam_physpkg_is('cam5')`, `cam_chempkg_is('trop_mam3')`), literal
  module parameters, and a short list of justified constants.  A site is
  `enabled`, `disabled` or `undecided`; the evaluator never guesses, and the
  record lists every undecided static-looking condition.
- **Two closures.** The static closure is everything reachable from
  `phys_run1` and `phys_run2`; the configured closure drops the edges the
  configuration rules out.  Procedures only in the static closure are
  `config_disabled`.  Procedures whose body opens with an `if (...) return`
  the configuration decides true are marked inert.  Initialization
  (`phys_init`) is inventoried separately because it produces the hidden
  state the kernels read.
- **Attribution to the plan.** Each plan action is tied to the procedures it
  runs: by its operation name, by the stage block of freeCAM's patched
  `physpkg` (tphysbc stage *N* is plan id 420+*N*, tphysac stage *N* is
  401+*N*), and by reviewed overrides.

## Categories

The rules decide a category for every procedure; the default is
`numeric_kernel`, because the closure's purpose is to open procedures, not
to hide them.

| Category | Meaning |
| --- | --- |
| `numeric_kernel` | computes something the model's answer depends on; in scope at every depth of the tree |
| `process_control` | the step's own control flow in `physpkg` |
| `internal_service` | history buffers, physics-buffer access, communication, grids, clocks, constants, allocators, forcing-file readers and their time interpolation |
| `out_of_scope` | dynamical core and coupler interface routines the physics happens to call |
| `config_disabled` | reachable in the source, ruled out by the configuration |
| `inert_in_configuration` | entered, but returns at once under this configuration |

## Open items the record names

- **Undecided guards.** 197 static-looking conditions on sites
  whose targets are numerical remain undecided (`dosw`, `dolw`, species
  indices such as `elec_ndx > 0`, flags set from module state at
  initialization).  They stay undecided until a reviewed constant or selector
  justifies them; nothing is excluded on a guess.
- **Type-bound calls through containers.** 9 `call obj%list%method`
  sites in `micro_mg_data` (a dynamic vector of post-processing steps) are
  not resolved statically.
- **Dummy procedures.** Procedure arguments (`compute_molec_diff`,
  `vd_lu_qdecomp` in `compute_vdiff`) are recorded as indirect calls; the
  actual procedures passed at each caller are the next phase's concern.
- **Function calls inside expressions.** 333 sites call a numerical
  procedure from inside an expression.  Replacing one of these in the model
  means hoisting the call into a temporary in the runner's piece and gating
  that site separately; sites that cannot stay bit-for-bit will be recorded
  as blocked, not hidden.
- **Helpers called per grid point inside loops.** 489 numerical sites
  sit inside `do` loops.  Such a helper is opened for standalone calls and
  data capture; its in-model replacement unit is the enclosing loop-level
  call, and the record's loop depth marks the candidates.

## Three representative entries

Before batches, the inventory's generic pieces were proved on three routines of
different shapes.  Each has a reviewed contract under `native/pi_cam/functions/`,
a standalone image linked from the oracle's own objects, and a Python call
through `load_function`.

| Routine | Shape | Standalone | In the model |

| `cloud_fraction::cldfrc_fice` | chunk subroutine called inside `zm_conv_evap`, itself a kernel | image built, `tmelt` verified against the model; every frame captured at its hook in a 50-step run (51200 calls) replayed bit-for-bit | first through a hoisted copy of `zm_conv_evap`: **not** bit-for-bit (one rank, a few ULP, step 7; the failure is kept as [`pi_cam_pausable_fice-pause_50step_failure.json`](../validation/pi_cam_pausable_fice-pause_50step_failure.json)); then a hook: `zm_conv.o`'s one reference is renamed to it, and the original answers at the hook bit-for-bit, 51200 pauses in 50 steps |

The failure in the last row shaped what followed.  Hoisting a routine
verbatim into a module works for drivers, whose arithmetic is incidental; it
does not reproduce the oracle object's rounding for a numerical routine, because
a recompiled copy vectorises and fuses differently.  No further numerical
routine is hoisted.

## Hooks: a call inside a compiled kernel, without hoisting

A hook leaves every numerical object's machine code untouched and changes only
where one call lands.  [`native/pi_cam/hooks.yaml`](../native/pi_cam/hooks.yaml)
names each hooked kernel, its function contract, and the caller objects; the
device build extracts those objects from the oracle archive and redirects the
reference in the object's symbol table (`objcopy --redefine-sym` when the callee
is in another object; when the callee is defined in the caller's own object its
definition is weakened and given a second name, and the hook, a strong
definition of the original name, wins the link).  The build proves the `.text`
bytes are unchanged and records every redirection in the image manifest.

The hook itself is a generated Fortran procedure with the callee's argument
list (`pycam_hooks.F90`, from the contracts).  It counts every call.  Unarmed,
it calls the original and returns.  Armed -- the owning stage class has a
replacement installed -- it records the frame and yields the stage's *fiber*: a
second execution stack (`pycam_fiber.c`, `ucontext`) the runner starts its
state machine on when a hooked kernel is replaced.  The yield returns control
to the runner's `start` or `resume` entry in the main context, which reports
NEEDS_PYTHON_KERNEL to Python exactly as a runner-level pause does; `resume`
switches back and the hook returns to its caller.  Fortran never calls Python;
it switches stacks.  A stage with no hooked kernel replaced never touches the
fiber, and a runner with no hooked kernels renders byte-identically to before.

The first image linking two hooked runners failed its deep convection gate
before the first pause: both runners had bound their fiber body to the bare C
name `fiber_body`, the archive link kept the shallow convection runner's, and
the deep runner's fiber ran the other state machine.  The record is
[`pi_cam_pausable_fice-hook_50step_failure.json`](../validation/pi_cam_pausable_fice-hook_50step_failure.json);
fiber bodies now carry their runner's prefix, and the device build refuses any
global symbol two support objects define.

## The execution inventory: counting kernels in place

Static reachability is not execution evidence, so a counting image measures
the real thing.  [`tools/build_pi_cam_kernel_observability.py`](../tools/build_pi_cam_kernel_observability.py)
classifies every candidate -- whether a count-only entry can take its symbol,
which call paths that entry covers, and which stay blind spots (inlined call
sites, internal procedures), each with its reason -- into
[`pi_cam_kernel_observability.json`](../validation/pi_cam_kernel_observability.json).
A counting image (`FREECAM_KCOUNT_SCOPE` at build time) weakens each counted
kernel's definition and puts a three-instruction trampoline under its name:
increment `counts[kernel][context]`, jump to the original.  A tail jump
forwards every register and stack byte untouched, so no calling convention is
guessed, nothing returns to Python, nothing allocates, and no floating-point
operation changes; a kernel whose symbol a replacement hook owns is counted by
chaining the trampoline between the hook and the original, so every call
counts exactly once.  Python owns attribution: the driver sets the process
slot around every workflow action (paired and exception-safe), initialization
and finalize count separately, and per-step total diffs record first and last
executing steps.  Counting is off in production images and refused outside
the single-threaded configuration.

`--observe-kernels` writes the raw observation;
[`tools/record_kernel_runtime_coverage.py`](../tools/record_kernel_runtime_coverage.py)
merges it with the observability inventory and the run's bit-for-bit record
into `pi_cam_kernel_runtime_coverage_<label>.json`, keeping execution evidence
and instrumentation coverage apart: *observed* (counted calls, lower bounds
where coverage is partial), *not observed in this run* (complete coverage, a
clean bit-for-bit run, zero calls), *unknown* (everything else -- absence of a
count is never evidence).  Batch A gated the mechanism on `cldfrc_fice`: the
counting image ran the 50-step case bit-for-bit with zero pauses (7355154),
and the per-process counts reconcile exactly with the hook evidence (51200
calls at the `zm_conv` site, 51200 more from the water-tracer path under deep
convection, 51200 under the cloud stage, 6144 in initialization, uniform
across all 512 ranks).

## Which candidates a hook can reach

The hook path applies only to calls the linked objects reach through a
relocation.  `compute_alpha`, the inlined function of `compute_uwshcu`, has
none, and no hook can reach it.  [`tools/audit_pi_cam_call_relocations.py`](../tools/audit_pi_cam_call_relocations.py)
reads the oracle archive the image links (`readelf` on every object) and
records, for each of the inventory's 601 candidates, the objects
defining its symbol and the objects whose text sections reference it:
[`pi_cam_kernel_api_redirectable_calls.json`](../validation/pi_cam_kernel_api_redirectable_calls.json)
(`--check` proves it current).

| Classification | Count | Meaning |
| --- | --- | --- |
| rename-references | 332 | every reference comes from another object: the `cldfrc_fice` mode |
| weaken-definition | 96 | a reference comes from the defining object itself: the `fluxbelowinv` mode |
| no-call-relocation | 135 | the symbol is defined but no text section references it: inlined at every call site (123 of them have every source caller in the same file, where ifort inlines at `-O2`), like `compute_alpha` |
| not-in-archive | 38 | an internal procedure the compiler absorbed into its host: no symbol of its own |

So 428 of the 601 candidates have a call a hook can redirect, and
173 do not.  This is a static reading of the linked
objects: a relocation is a compiled call site, not proof this configuration
executes it (the call-tree inventory says that), and a redirectable call is not
yet a hooked kernel -- the hook needs a function contract the frame can serve,
and 113 of the 428 take `state`, `pbuf` or a tendency
derived type, which the contracts do not express yet.  Routines a hook cannot
reach remain callable standalone where a contract exists, and a routine with
no call of its own (`virtem`, inlined into its loop) is reached through the
runner's pause at the enclosing statement.  None of this covers every routine
at every depth; the record says which.

## Runtime evidence

Static reachability is never narrowed by a count of zero.  The record
carries, per plan action, the activity the decoupling ledger recorded in the
50-step and month runs, and, per kernel already opened, its in-model gates.
Per-procedure call counts from an instrumented original run are a later
addition; when they arrive they annotate, they do not exclude.
