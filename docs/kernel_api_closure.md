# The kernel-API closure: inventory of the PI-atm physics call tree

freeCAM opens CAM physics to Python one numerical kernel at a time.  The
[decoupling ledger](../validation/physics_kernel_decoupling.json) follows the
kernels that are already open; this page is about everything else: the
complete set of procedures the configured physics step can reach, so that
opening the rest is a list to work through rather than a search.

The record is
[`validation/pi_cam_kernel_api_closure.json`](../validation/pi_cam_kernel_api_closure.json),
generated by `tools/build_pi_cam_kernel_api_closure.py` from the pinned iCESM
source and the rules in
[`native/pi_cam/kernel_api_closure_rules.yaml`](../native/pi_cam/kernel_api_closure_rules.yaml).
`--check` proves the committed record still matches the pinned source, the
rules, the generator and the reference case's configuration; the unit suite
runs that check.

## How the tree is built

- **The build's sources, in the build's order.** The rules list the
  directories of the reference case's `Filepath`; the first directory holding
  a basename wins, exactly as the CESM build resolves it (so the RRTMG copies
  of `radiation`, `cloud_rad_props` and `radconstants` are the ones analysed,
  and CARMA, CLUBB, WACCM and CAM4 code is not).  The `genf90` templates are
  expanded the way the build expands them.
- **The configuration's macros.** Every file goes through `cpp` with the
  case's `CESM_cppdefs` and the machine macros (`SPMD`, `MODAL_AERO_3MODE`,
  `PCOLS=16`, ...), verified against the image manifest's compile command.
  Lines the preprocessor removes never count; every surviving line under a
  conditional carries its condition.
- **Fortran scoping, not name matching.** fparser parses each file; every
  `call` and every reference that could be a function (`Part_Ref`,
  structure-constructor-shaped references) is resolved through locals,
  dummies, host association, `use` with `only` and renames (transitively
  through re-exporting modules), generic interfaces, internal procedures,
  external units, `associate` aliases and type-bound bindings.  A name that
  resolves to a variable or a type is not a call; a name that resolves to
  nothing is recorded as unresolved rather than dropped.
- **Every call site, with its context.** Each site records the original
  line, the preprocessor condition, the enclosing `if`/`select case`
  branches (with negations for `else`), the loop depth, and whether the
  callee is a plain `call`, a function inside an expression, or an actual
  argument of another call.
- **Configuration guards, decided or left open.** Branch conditions are
  evaluated tri-state against the reference run's namelist selectors
  (`deep_scheme`, `microp_scheme`, `use_gw_oro`, ...), the case's build
  options (`cam_physpkg_is('cam5')`, `cam_chempkg_is('trop_mam3')`), literal
  module parameters, and a short list of justified constants.  A site is
  `enabled`, `disabled` or `undecided`; the evaluator never guesses, and the
  record lists every undecided static-looking condition.
- **Two closures.** The static closure is everything reachable from
  `phys_run1` and `phys_run2`; the configured closure drops the edges the
  configuration rules out.  Procedures only in the static closure are
  `config_disabled`.  Procedures whose body opens with an `if (...) return`
  the configuration decides true are marked inert.  Initialization
  (`phys_init`) is inventoried separately because it produces the hidden
  state the kernels read.
- **Attribution to the plan.** Each plan action is tied to the procedures it
  runs: by its operation name, by the stage block of freeCAM's patched
  `physpkg` (tphysbc stage *N* is plan id 420+*N*, tphysac stage *N* is
  401+*N*), and by reviewed overrides.

## Categories

The rules decide a category for every procedure; the default is
`numeric_kernel`, because the closure's purpose is to open procedures, not
to hide them.

| Category | Meaning |
| --- | --- |
| `numeric_kernel` | computes something the model's answer depends on; in scope at every depth of the tree |
| `process_control` | the step's own control flow in `physpkg` |
| `internal_service` | history buffers, physics-buffer access, communication, grids, clocks, constants, allocators, forcing-file readers and their time interpolation |
| `out_of_scope` | dynamical core and coupler interface routines the physics happens to call |
| `config_disabled` | reachable in the source, ruled out by the configuration |
| `inert_in_configuration` | entered, but returns at once under this configuration |

## Open items the record names

- **Undecided guards.** 197 static-looking conditions on sites
  whose targets are numerical remain undecided (`dosw`, `dolw`, species
  indices such as `elec_ndx > 0`, flags set from module state at
  initialization).  They stay undecided until a reviewed constant or selector
  justifies them; nothing is excluded on a guess.
- **Type-bound calls through containers.** 9 `call obj%list%method`
  sites in `micro_mg_data` (a dynamic vector of post-processing steps) are
  not resolved statically.
- **Dummy procedures.** Procedure arguments (`compute_molec_diff`,
  `vd_lu_qdecomp` in `compute_vdiff`) are recorded as indirect calls; the
  actual procedures passed at each caller are the next phase's concern.
- **Function calls inside expressions.** 333 sites call a numerical
  procedure from inside an expression.  Replacing one of these in the model
  means hoisting the call into a temporary in the runner's piece and gating
  that site separately; sites that cannot stay bit-for-bit will be recorded
  as blocked, not hidden.
- **Helpers called per grid point inside loops.** 489 numerical sites
  sit inside `do` loops.  Such a helper is opened for standalone calls and
  data capture; its in-model replacement unit is the enclosing loop-level
  call, and the record's loop depth marks the candidates.

## Runtime evidence

Static reachability is never narrowed by a count of zero.  The record
carries, per plan action, the activity the decoupling ledger recorded in the
50-step and month runs, and, per kernel already opened, its in-model gates.
Per-procedure call counts from an instrumented original run are a later
addition; when they arrive they annotate, they do not exclude.
