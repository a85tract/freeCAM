末端设备由 device.yaml 描述。构建器使用固定版本的 CCPP parser 从 7 个 suite XML 中发现 155 个活跃 scheme，并同时读取每个 .meta 和原始 .F90，核对 entrypoint、 intent、rank、dimension、kind 和 units，随后生成 adapter、symbol version map 与 device.json。

1 · 数据总线

StatePool 为字段保存内部名称、CCPP standard_name、dtype、shape、units、intent 和所有权。device 不需要知道某个数组在 Python 中叫 T 还是 air_temperature。

2 · 自动连接器

生成的 adapter 只处理 C ABI、错误字符串和原始 subroutine 调用，不包含 Kessler 方程。Python 通过 manifest 动态构造 ctypes 签名。

3 · 末端计算设备

155 个 scheme 都有自动生成的 connector：100 个原始 Fortran device 已干净构建，29 个纯 history scheme 由 Python host service 执行；另外 26 个仍明确等待 MPI/I/O/外部源码等服务，不把“生成接口”冒充“已经科学验证”。

Responsibility map

谁在和谁交互？

“server”不是模型计算器，“Dask Scheduler”也不是 MPI rank。把控制面、资源面和数据面分开后，整个架构就很清楚。

S

自定义 Server

连接 Notebook 与一个已经存活的24-rank模型。

  • rank 0 socket 接收
  • 保持 live StatePool
D

Dask

连接 Notebook 中的实验意图与可重启任务。

  • Client 提交 Future
  • Scheduler 管依赖
  • Worker 执行 action plan

  • 提供 PBS_NODEFILE

  • halo exchange
  • bcast / gather / allreduce
  • barrier 与一致性

DeviceRegistry

把通用 StatePool 字段连接到生成的 scheme device。

  • 验证 dtype/shape/units

Dask 可以替代我们自己编写的“实验任务提交与依赖管理”，但每个 CAM segment 内部仍然由 mpi4py 完成紧耦合通信。

PBS behavior

“一个job”到底指什么？

一个 PBS job 可以包含多个 Dask task 和多次 mpiexec。task 数量、MPI segment 数量和 PBS job 数量不是同一个概念。

allocation 模式

qsub -I ... ncpus=25:mpiprocs=24
  └─ Jupyter + Dask scheduler/worker
       ├─ base task        → mpiexec -n 24
       ├─ control task     → mpiexec -n 24
       ├─ no-kessler task  → mpiexec -n 24
       └─ warm task        → mpiexec -n 24

所有 summary 的 pbs_job_id 相同；分支目录里没有 job.pbs，也不调用嵌套 qsub。

保留的 PBS-per-segment 模式

Jupyter on login node
  └─ Dask scheduler/workers
       ├─ base task        → qsub job A
       ├─ control task     → qsub job B
       ├─ no-kessler task  → qsub job C
       └─ warm task        → qsub job D

此时 summary 会显示 execution_mode="pbs" 和不同 PBS job IDs；它是兼容模式，不是当前推荐的单-allocation演示。

Common questions

容易混淆的关键边界

这些问题都来自“任务、进程、状态和资源”四个层次被放在同一句话里。展开即可看到清晰边界。

Dask 可以让同一批 MPI ranks 一直活着吗？

当前 task/checkpoint 模式不可以。Dask Worker 只启动并等待一个 MPI segment；segment结束后进程退出。要控制同一批live ranks，仍需常驻 server 或等价的持久IPC。

细粒度 action 是否每次都重新启动 MPI？

不一定。一个 SegmentPlan 内的所有 action 共用同一次24-rank MPI启动和同一个live StatePool；只有使用 submit_action() 把边界变成新的Future时，才会结束当前segment、写checkpoint并为下一个task重新启动MPI。

为什么单-allocation模式仍然需要几分钟？

它只去掉了每个分支重新排PBS队列的时间。模型step、MPI进程启动、24-rank checkpoint恢复与写入仍然真实发生；一个worker还会让占满24 ranks的segments串行执行。

串行执行意味着后一个分支读取前一个分支吗？

不意味着。control和no-kessler都从base的不可变snapshot创建私有副本；warm从它明确指定的parent创建副本。串行只是资源安排，不是状态依赖。

自定义 server 为什么需要 socket？

因为Notebook和24-rank模型是不同进程。模型完成一条命令后要继续存活并等待下一条命令，就必须有socket、pipe、ZeroMQ或MPI intercommunicator之类的持久IPC。当前实现使用带authkey的socket。

为了接入 Kessler，是否改写了原始 Fortran 数值代码？

没有。构建器读取固定 CAM-SIMA revision 中的原始 kessler.F90 和 CCPP metadata，生成一个只负责 ABI 转换的 adapter。原始 scheme 直接参与 device .so 编译；旧的手写 kessler_kernel.F90 已删除。

任意 CCPP scheme 现在都能无条件自动接入吗？

所有 155 个活跃 scheme 都会自动得到 connector 与机器可读状态，但这不等于全部都已科学运行。通用 ABI 已覆盖 real/integer/default-logical、fixed-width character、Python-owned shaped allocatable arrays 和 non-allocatable derived state；纯 history scheme 由 Python service 接管。当前 100 个 native device 加 29 个 host service 可执行；仍依赖 MPI reduction、PIO/NetCDF input、外部 MUSICA 源码或 allocatable object 的 26 个 scheme 会 fail closed，并在 all_scheme_support.json 写明原因。
